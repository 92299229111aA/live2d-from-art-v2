# 兔耳和服半身项目复盘

记录依据：本次阶段报告、实际 VTS 加载画面与用户反馈。浏览器检查通过；VTS 1.35.10 实际识别模型、加载纹理、生成 13 条自动映射，摄像头曾显示 15 FPS / 84% confidence。随后用户指出上半身除头部外近似静态并要求先讨论垂臂改造；五分钟会话未完成。不能写 VTS 全部通过或发布就绪。

## 做得有效

- 原图不可覆盖、坐标保真、局部补底，保留角色脸和配色。
- 静态 MOC 起步，分阶段回退；实际 Core 抓图与单参数检查发现闭眼残影、嘴角分离、重复眉毛和边缘白底。
- 运行包按引用打包；区分 Core DLL 加载与 VTS 应用内加载。

## 做得不好与改进

| 问题 | 原因/实际影响 | 下次改变 |
|---|---|---|
| 身体“会动”但直播中近乎静态 | 本例身体 Z 约 ±0.8°、头 Z 约 ±3°，偏保守；技术变化被当成动作质量佐证 | 在目标头像尺寸下做身体动作早期评审；显示实际位移/角度，技术与可感知视觉分开验收 |
| 举手/伸手姿势直到后期才成为问题 | 保真优先正确，但未充分确认长期直播姿态 | 基准阶段就展示胸像与半身，提出遮挡和换姿成本；不默认擅自重画 |
| 自定义浏览器物理与导出 physics3 不一致 | 预览通过不能预测 VTS 的求解结果 | 用相同资源和兼容求解器；目标平台提前验证 |
| VTS 自动映射越过作者参数范围 | 自动眼开输出 1.9、嘴开 2.1，头部 ±30，与本例范围不同 | 逐项对照 MOC 范围并实测，不能仅凭自动配置成功报告绑定通过 |
| 最终 PSD 落后于 MOC | 运行派生布局包含后续眉毛/边缘修正 | 由唯一权威布局重导出或明确历史版本；资产哈希关联 QA |
| 原画中性态与直播休息态混淆 | 原图张嘴；“全部参数归零”又会闭眼 | 分离 reference_pose、tracking_rest、debug_reset 预设 |
| 步骤多、需要反复“继续” | 长阶段提示和状态依赖对话 | project.json + 自动推进；阶段是内部质量门禁，不是重复许可 |
| 先建议游戏捕获，随后才解释无 UI 输出 | 捕获透明与隐藏操作界面是两件事 | Windows OBS 默认介绍 Spout2；不安装时才给游戏捕获备选 |
| VTS 开启 GPU 优先级与游戏帧率优先目标冲突 | 优先级是资源调度，不是资源节省 | 明确优化目标，做同场景 A/B 测试，不许诺零性能影响 |

## 可简化与不可省略

可自动化：输入哈希、目录/状态、引用检查、增量构建、参数矩阵抓图、白名单打包、证据索引、资产新鲜度校验。

保留人工判断：角色身份、姿态选择、遮挡补绘质量、动作可感知程度、组合姿态穿模、实际面捕自然度。用户无需提供四阶段长提示，但仍需原图和必要时的一次面捕配合。

此案例的 158 ArtMesh、36 参数、4096 图集不是下一角色的目标规格。不能把兔耳/马尾坐标或配色阈值当作通用值。原图和生成素材不随技能发布。
